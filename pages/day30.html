Parametrized Testing —
50 SSIDs × 1 Test Function

Your WLAN fleet has 50 APs. Without parametrization, you'd write 50 identical test functions. With @pytest.mark.parametrize and a CSV file, you write one test function that runs 50 independent test cases — each with its own pass/fail, its own name, and its own failure message.

⏱~50 min
🐍Python 3.9+
📦pytest · csv
🔄@parametrize · ids · csv loading
🤔

The 'Why' — Conceptual Breakdown

The Fleet Testing Problem

An enterprise WLAN deployment has dozens to hundreds of APs. Your acceptance test requires verifying each AP individually: correct SSID, correct channel, correct security, RSSI above threshold. Writing one test per AP is unmaintainable — adding a new AP means editing test code.

Parametrization drives test data from external sources.
Load AP configurations from a CSV file, a JSON inventory, or a database. Each row becomes a test case with its own name and failure context. When you add a new AP to the inventory, it automatically appears as a new test case — no code changes required.

The ids Parameter

By default, pytest names parametrized cases test_func[param0-param1]. With the ids parameter, you get meaningful names like test_rssi[CorpWifi-5G] — essential for reading CI reports when a specific AP fails.

Code Walkthrough — @parametrize, ids, and Loading from CSV

Create test_parametrized.py. The parametrize examples progress from simple inline data to CSV-driven fleet testing.

Block 1 — Basic @parametrize with ids
Python test_parametrized.py 
# =============================================================
# Day 30: Parametrized WLAN Tests
# Run with: pytest test_parametrized.py -v
# =============================================================

import pytest
import csv
from pathlib import Path

def classify_signal(rssi):
    if rssi >= -50: return "Excellent"
    if rssi >= -60: return "Good"
    if rssi >= -70: return "Fair"
    return "Poor"

# ── Block 1: Simple parametrize with explicit ids ──────────────

@pytest.mark.parametrize("rssi,expected", [
    (-42, "Excellent"),
    (-55, "Good"),
    (-65, "Fair"),
    (-80, "Poor"),
    (-50, "Excellent"),   # Boundary: -50 = Excellent
    (-51, "Good"),        # Boundary: -51 = Good
], ids=[
    "excellent",
    "good",
    "fair",
    "poor",
    "boundary_excellent",
    "boundary_good",
])
def test_classify_rssi(rssi, expected):
    """RSSI classification must map each dBm range to the correct label."""
    result = classify_signal(rssi)
    assert result == expected, f"classify_signal({rssi}) = '{result}', expected '{expected}'"
Block 2 — Multi-Parameter AP Fleet Test

When parametrizing with multiple columns (like AP properties), each test case is a tuple of values. The ids list assigns meaningful names based on the AP's SSID.

Python 
# AP fleet data: (ssid, bssid, rssi, channel, security)
AP_FLEET = [
    ("CorpWifi-5G",  "AA:BB:CC:01:02:03", -52, 36,  "WPA2"),
    ("CorpWifi-2G",  "AA:BB:CC:01:02:04", -68, 6,   "WPA2"),
    ("GuestWifi",    "AA:BB:CC:01:02:05", -71, 11,  "WPA2"),
    ("PrinterNet",   "AA:BB:CC:01:02:06", -55, 1,   "WPA2"),
    ("IoTNetwork",   "AA:BB:CC:01:02:07", -60, 6,   "WPA2"),
]

@pytest.mark.parametrize(
    "ssid, bssid, rssi, channel, security",
    AP_FLEET,
    ids=[ap[0] for ap in AP_FLEET]   # Use SSID as the test name
)
def test_ap_rssi_compliance(ssid, bssid, rssi, channel, security):
    """Each AP must have RSSI above -75 dBm."""
    assert rssi >= -75, f"AP '{ssid}' ({bssid}) has RSSI {rssi} dBm — below -75 dBm threshold"

@pytest.mark.parametrize(
    "ssid, bssid, rssi, channel, security",
    AP_FLEET,
    ids=[ap[0] for ap in AP_FLEET]
)
def test_ap_security_compliance(ssid, bssid, rssi, channel, security):
    """Each AP must use WPA2 or WPA3 — no open or WEP networks allowed."""
    approved = {"WPA2", "WPA3", "WPA2/WPA3"}
    assert security in approved, (
        f"AP '{ssid}' uses '{security}' — not in approved security types {approved}"
    )
Block 3 — Loading Test Cases from CSV

When your fleet grows to 50+ APs, hardcoding them in test files becomes impractical. Loading from CSV means your inventory and your tests are the same source of truth — update the CSV, tests update automatically.

Python 
def load_ap_params_from_csv(csv_path):
    """
    Load AP test parameters from a CSV file.
    Returns a list of pytest.param objects with SSID as the test ID.
    """
    params = []
    try:
        with open(csv_path) as f:
            reader = csv.DictReader(f)
            for row in reader:
                params.append(pytest.param(
                    row["ssid"],
                    row["bssid"],
                    int(row["rssi_dbm"]),
                    int(row["channel"]),
                    row["security"],
                    id=row["ssid"]   # Named test case
                ))
    except FileNotFoundError:
        pass   # No CSV yet — parametrize with empty list (0 tests)
    return params

# Load from CSV (falls back to empty list if file doesn't exist)
CSV_PATH = Path("test_results.csv")
csv_params = load_ap_params_from_csv(CSV_PATH)

@pytest.mark.parametrize(
    "ssid, bssid, rssi, channel, security",
    csv_params or [pytest.param("demo", "AA:BB:CC", -60, 6, "WPA2", id="demo")]
)
def test_fleet_from_csv(ssid, bssid, rssi, channel, security):
    """Fleet test loaded from CSV — one test case per AP row."""
    assert rssi >= -80, f"'{ssid}' RSSI {rssi} dBm"
    assert security in {"WPA2", "WPA3"}, f"'{ssid}' security '{security}'"
