The 'Why' — Conceptual Breakdown

The "Works on My Machine" Problem

You write a great WLAN automation script. It imports scapy, netifaces, and paramiko. You hand it to a colleague. They run it and immediately see: ModuleNotFoundError: No module named 'scapy'. You spend 30 minutes figuring out which version of which library they need. This is the most common friction point in shared Python projects — and it is entirely preventable.

A virtual environment is a self-contained Python sandbox.
Every project gets its own isolated set of installed packages with pinned version numbers. You share the requirements.txt file, and anyone can recreate your exact environment with one command.

Global vs. Isolated Installs

When you install a package globally (pip install scapy without activating a venv), it lands in the system Python's shared folder. Project A needs scapy==2.4.5 while Project B needs scapy==2.5.0. They can't coexist globally. Virtual environments solve this by giving each project its own completely separate package directory. Activate the venv, and Python reads packages only from that folder — everything else is invisible.

The pip Ecosystem

pip (Pip Installs Packages) is Python's built-in package manager. It downloads packages from PyPI (the Python Package Index) — over 500,000 open-source libraries covering everything from HTTP clients to hardware drivers to ML frameworks. For WLAN automation, we rely on packages like Scapy, netifaces, dnspython, and pytest — all installed via pip in seconds.

Code Walkthrough — Mastering venv & pip

Follow these blocks in order. By the end you'll have a proper project environment and a script (Day05_env_check.py) that verifies every required package is installed and reports its version — a pattern used in real CI pipelines.

Block 1 — Creating and Activating a Virtual Environment

The venv module is built into Python 3.3+ — no installation needed. It copies a minimal Python interpreter into a local venv/ folder so your project becomes completely self-contained.

Bash Terminal 
# Navigate to your project folder
cd wlan-automation-course

# Create the virtual environment (creates a 'venv/' folder)
python3 -m venv venv

# Activate it — your prompt changes to (venv) to confirm
# macOS / Linux:
source venv/bin/activate

# Windows PowerShell:
.\venv\Scripts\Activate.ps1

# Confirm you're using the venv Python (not system Python)
which python          # macOS/Linux → should point inside venv/bin/
python --version
Block 2 — Installing Packages with pip

With the venv active, pip install puts packages only inside the venv folder. The == syntax pins an exact version — critical for reproducibility in CI pipelines and shared test environments.

Bash 
# Always upgrade pip first — older versions miss security fixes
pip install --upgrade pip

# Install our core course libraries
pip install netifaces psutil

# Install with a minimum version constraint
pip install "requests>=2.28"

# Install with an exact version pin (best for CI reproducibility)
pip install "netifaces==0.11.0"

# Inspect a package's metadata
pip show netifaces
Block 3 — Freezing to requirements.txt

pip freeze prints every installed package with its exact version. Redirecting that output to requirements.txt captures a complete environment snapshot. Anyone can replicate it exactly with pip install -r.

Bash 
# Capture the current environment
pip freeze > requirements.txt

# View the file — every package is pinned to an exact version
cat requirements.txt
# netifaces==0.11.0
# psutil==5.9.5
# requests==2.31.0

# Recreate the exact same environment on another machine:
pip install -r requirements.txt
Block 4 — The env_check.py Preflight Script

Create Day05_env_check.py. This script validates your environment before running any automation. Catching missing packages early with a clear error is far better than a confusing traceback deep inside your test suite.

Python Day05_env_check.py 
# =============================================================
# Day 5: Environment Verification (Preflight Check)
# Purpose: Confirm all required packages are installed before
#          running any automation — catches problems early.
# =============================================================

import sys
import importlib.metadata   # Built-in: reads installed wheel metadata

# Map import names → PyPI package names
# (They sometimes differ, e.g. 'cv2' package is 'opencv-python')
REQUIRED_PACKAGES = {
    "netifaces": "netifaces",
    "psutil":    "psutil",
}

def check_python_version(min_major=3, min_minor=9):
    """Verify Python version meets the course minimum."""
    major = sys.version_info.major
    minor = sys.version_info.minor
    ok = (major, minor) >= (min_major, min_minor)
    status = "✓" if ok else "✗ FAIL"
    print(f"  [{status}] Python {major}.{minor}  (need {min_major}.{min_minor}+)")
    return ok

def check_package(import_name, pypi_name):
    """
    Try to read an installed package's version metadata.
    Returns True if found, False if missing.
    """
    try:
        # importlib.metadata.version() reads the installed wheel metadata file
        version = importlib.metadata.version(pypi_name)
        print(f"  [✓] {import_name:15s}  version {version}")
        return True
    except importlib.metadata.PackageNotFoundError:
        print(f"  [✗] {import_name:15s}  NOT INSTALLED")
        print(f"      → Fix: pip install {pypi_name}")
        return False

def main():
    print("=" * 50)
    print("  WLAN Automation — Environment Preflight Check")
    print("=" * 50)

    all_ok = True

    # Check Python version first — wrong version breaks everything
    print("\n[Python Version]")
    if not check_python_version():
        all_ok = False

    # Check each required package
    print("\n[Required Packages]")
    for import_name, pypi_name in REQUIRED_PACKAGES.items():
        if not check_package(import_name, pypi_name):
            all_ok = False

    print("\n" + "=" * 50)
    if all_ok:
        print("  ✓ All checks passed — environment is ready!")
    else:
        print("  ✗ Some checks FAILED — fix the issues above.")
        sys.exit(1)   # Non-zero exit code signals failure to CI pipelines
    print("=" * 50)

if __name__ == "__main__":
    main()
Block 5 — Deactivating and Recreating from Scratch

Knowing how to cleanly destroy and recreate a venv is the CI workflow. Every GitHub Actions pipeline run starts with a fresh environment and rebuilds from requirements.txt to ensure tests never rely on stale state.

Bash 
# Leave the virtual environment (back to system Python)
deactivate

# Safely delete just the venv folder — your code files are untouched
rm -rf venv

# Rebuild from requirements.txt (what CI does on every run)
python3 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt

# Run the preflight check to confirm everything is correct
python Day05_env_check.py
